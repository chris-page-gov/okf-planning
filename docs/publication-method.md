# Build and publication method

This repository publishes an independent, draft and unverified planning
metadata snapshot. The build is offline by default. It does not query live
planning systems and does not imply endorsement by MHCLG or any source
publisher.

## Semantic meaning and publication lifecycle

[`okf.semantic.json`](../okf.semantic.json) records the meaning and limits of
the generated Markdown, YAML-LD, JSON-LD and Explorer projections.
[`okf.publication.json`](../okf.publication.json) records the separate build,
assurance, documentation and Pages lifecycle.

The publication contract is data, not a shell script. Review every declared
command against `AGENTS.md` and the repository code before running it.

## Authored and generated boundaries

The source family consists of the two frozen JSON files under `source/` and the
explicit curated records in `src/okf_planning/sources.py`. The generator owns
`bundle/concepts/`, `bundle/context/`, `bundle/data/` and the generated root
files listed in `src/okf_planning/build.py`.

`bundle/index.html`, `bundle/app.js` and `bundle/styles.css` are hand-authored
site assets inside the publication directory. The generator deliberately
preserves them. `bundle/checksums.json` covers generator-owned files, not those
three assets or the packaging-only `.nojekyll` marker; the Git commit is their
current identity boundary.

For a source or generator change:

1. Review the source, authority, rights and snapshot boundary.
2. Run `python3 scripts/build_bundle.py` once.
3. Inspect the complete `bundle/` diff and do not hand-edit generated files.
4. Run `python3 scripts/check_okf.py`, `pytest`, the publication-contract check
   and the documentation-lockstep check.
5. Commit the source, generated projections, affected documentation and
   `CHANGELOG.md` together.

Source acquisition is a separate, networked and deliberate step. It validates
both upstream payloads before replacing either source file and still requires
a reviewed offline build before publication.

## CI candidate reuse

The Pages workflow builds the bundle once, validates it, and requires
`git diff --exit-code` to prove the generated bytes match the commit. It then
adds the empty `.nojekyll` packaging marker, checks the complete set of public
entry points and uploads that candidate. There is no second bundle build before
upload or in the deployment job.

Pull request validation uses a per-ref concurrency group and can cancel only an
obsolete run for the same pull request. Protected-main runs are non-cancelling,
and Pages publication uses a separate serial group.

## Current limitation

An exact-commit real-browser receipt is not yet integrated. Until it is, the
public Pages URLs are useful discovery entry points but are not evidence that a
particular deployed commit and browser journey were verified. A failed future
live check must be reported; it must not trigger a rebuild of the assured
candidate.
